为什么 架构 部署 排队 拓扑 流程 Workflow 接口 限制 接入 排障
基于 rayjob-submitter + KubeRay + GitHub Actions

多机 Ascend CI 的系统设计、原理与接入方法

从 GitHub Actions 发起，通过内部 HTTP submitter 创建 KubeRay RayJob， 最终在多机多卡 Ascend 集群上运行分布式训练。控制面、执行面、资源拓扑和 workflow 接入方式在同一套机制中闭环。

N x M worker 数 x 每 worker NPU 数，nightly 当前实例为 2 x 16
HTTP API GitHub Actions 不直接持有 Kubernetes 权限
模板化 RayJob YAML 固化安全约束，workflow 只做白名单调参

01 / 背景

为什么不让 workflow 直接创建 Kubernetes 资源

核心取舍是把 Kubernetes 权限、RayJob 模板和清理逻辑收敛到内部 submitter 服务， workflow 只描述本次任务的提交、镜像、入口脚本和资源调参。

背景与目标

核心观点： 目标不是在 Kubernetes 上手工运行一个 RayJob，而是把多机多卡训练稳定接入 CI。 CI 触发频繁、失败需要可观测、训练资源成本高、清理必须可靠，GitHub Actions 本身也不持有集群写权限。 HTTP submitter 承担受控网关角色：workflow 提交任务描述，submitter 根据模板创建 RayJob、观察状态和日志，并在 workflow 结束时清理资源。

这套设计保护了什么

  • GitHub Actions 不直接持有 Kubernetes kubeconfig。
  • workflow 不能提交任意 RayJob YAML，只能走白名单字段和安全 patch。
  • RayJob、RayCluster、Pod 日志和清理都由服务端统一封装。
  • 网页端强制终止 workflow 时，后台 stale cleanup 兜底删除残留任务。
  • 最小权限
  • 模板驱动
  • 状态可观测
  • 资源兜底清理

02 / 系统架构

控制面是 submitter，执行面是 KubeRay RayCluster

一次 CI 任务会穿过三层边界：GitHub runner、submitter 服务、KubeRay 管理的 RayJob/RayCluster。 一个 RayJob 主要创建 1 个 RayJob submitter Pod、1 个 head Pod 和 N 个 worker Pod；worker 数量由提交参数与服务端上限共同控制。

03 / 部署形态

控制面服务、队列资源和 RayJob 模板分层部署

部署面分为四层：KubeRay/Kueue 控制器、Kueue 队列资源、rayjob-submitter 服务、RayJob 模板。 GitHub Actions 只访问集群内的 submitter Service，不直接持有 Kubernetes 写权限。

部署产物

产物 位置 职责
submitter 镜像 Dockerfile 构建 Go 静态二进制，并把默认 templates/verl-rayjob.yaml 打进镜像。
RBAC deploy/rbac.yaml 创建 ci-system 命名空间、ServiceAccount，并在 ray 命名空间授予 RayJob 创建/查询/删除和 Pod 日志读取权限。
HTTP 服务 deploy/deployment.yaml 部署 rayjob-submitter Deployment 和 ClusterIP Service，暴露 /healthz 与 /api/v1/*。
RayJob 模板 templates/verl-rayjob*.yaml 固化 RayCluster 结构、hostPath、NPU 驱动挂载、nodeSelector、基础 env、workerGroup；启用 Kueue 时同时携带队列标签和 spec.suspend。
Kueue 队列 kueue/kueue-ray-npu-a2.yaml 定义 ResourceFlavor、ClusterQueue、LocalQueue 和 workload priority，把多机 RayJob 纳入资源准入。
业务流水线 nightly_ascend_multinode.yml 准备源码缓存、构造提交 payload、调用 submitter、消费 watch 事件并执行 cleanup。

kubectl -n ci-system rollout status deploy/rayjob-submitter

关键运行配置

配置 作用
TARGET_NAMESPACE=ray RayJob 创建到 ray 命名空间。
RAYJOB_TEMPLATE_PATH submitter 启动时加载的 RayJob 模板路径。
WORKER_REPLICAS / MAX_WORKER_REPLICAS 默认 worker 数和单次提交允许的最大 worker 数。
ALLOWED_IMAGE_PREFIXES 限制 workflow 可提交的镜像来源。
ALLOWED_SCRIPT_PREFIXES 限制入口脚本只能来自受控目录，例如共享缓存和 /verl。
MAX_ARGS / MAX_EXTRA_ENV / MAX_TEMPLATE_PATCHES 控制 workflow 单次提交的参数数量、环境变量数量和 template patch 数量。
STALE_RAYJOB_* 后台清理残留 RayJob，覆盖网页端强制终止 workflow 未执行 DELETE 的场景。
Kueue 生效依赖 submitter 实际加载的 RayJob 模板。仅部署 ClusterQueue / LocalQueue 不会自动拦截 RayJob； RAYJOB_TEMPLATE_PATH 指向的模板必须包含 kueue.x-k8s.io/queue-name、优先级标签和 spec.suspend: true。 仓库中的 templates/verl-rayjob-a2.yaml 展示了队列字段形态，硬件专用模板需要与目标 Kueue 资源和 NPU resource key 对齐。

04 / Kueue 资源准入

多机任务必须先排队，再整体进入调度

多机 RayJob 需要成组资源。没有队列准入时，多个任务同时创建 RayCluster，容易各自抢到一部分机器， 剩余资源又不足以让任何一个任务补齐完整拓扑，最终形成资源碎片和互相等待。

RayJob 接入 Kueue 的条件

配置点 作用
kueue.x-k8s.io/queue-name RayJob 进入指定 LocalQueue，例如 default。
kueue.x-k8s.io/priority-class 控制 workload 优先级，例如多机任务使用 ray-high。
spec.suspend: true RayJob 创建后先暂停，等待 Kueue 准入后再由控制器放行。
LocalQueue / ClusterQueue 把 ray 命名空间中的任务映射到统一资源池。
ResourceFlavor 按节点标签和资源名区分硬件池，例如 A2、A3、不同 NPU resource key。
RayJob 模板中的 Kueue 字段 队列标签由模板提供 
metadata:
  labels:
    kueue.x-k8s.io/queue-name: default
    kueue.x-k8s.io/priority-class: ray-high
spec:
  suspend: true
submitter 渲染 RayJob 时会保留模板已有 labels，并追加 CI 标签；安全 template_patches 不开放 metadata patch。 因此队列归属属于服务端模板和部署配置，不由 workflow 临时改写。

Kueue 资源对象

对象 示例 作用
WorkloadPriorityClass ray-high 多机 RayJob 使用更高优先级，支持队列内按优先级准入和抢占策略。
ResourceFlavor a2-normal / a2-dual 用节点标签绑定不同硬件池，并声明对应 CPU、memory、NPU quota。
ClusterQueue ray-npu-cq 集中管理 NPU 资源配额，使用 BestEffortFIFO 队列策略和优先级抢占。
LocalQueue default / ray RayJob 所在命名空间的入口队列，指向全局 ClusterQueue。
Namespace label kueue-pool=ray-npu 匹配 ClusterQueue 的 namespaceSelector，把目标命名空间纳入资源池。

05 / 拓扑模型

多机规模由 worker 数和单机资源共同决定

多机 CI 的核心规模参数不是固定节点数，而是 `worker_replicas x 每 worker NPU 数`。 当前 nightly 示例使用 2 个 worker、每个 worker 16 张 Ascend NPU，形成 32 卡验证拓扑。

worker_replicas

`worker_replicas` 控制 Ray worker Pod 数量。submitter 会把该值 patch 到 RayCluster worker group 的 `replicas/minReplicas/maxReplicas`。

服务端通过 `MAX_WORKER_REPLICAS` 控制当前环境允许的最大 worker 数，避免单条 CI 超出资源预算。

每 worker 资源

CPU、memory、NPU 数和 `/dev/shm` 通过 `template_patches` 调整。资源 patch 只作用于白名单路径，不能改 hostPath、权限、镜像和调度约束。

当前 nightly 示例把每个 worker 调整到 `64 CPU / 512Gi / 16 NPU / 128Gi dshm`。

训练并行规模

当训练使用所有 worker NPU 时，data parallel size 通常等于 `worker_replicas x 每 worker NPU 数`。

2 x 16 的 nightly 拓扑对应 DP size 32，mini batch、global batch 和并行策略都需要与该规模匹配。

规模化参数对照

维度 配置入口 当前 nightly 实例 影响范围
worker 数量 WORKER_REPLICAS / request worker_replicas 2 Ray worker Pod 数、训练节点数、跨节点通信规模。
单 worker NPU template_patches 中的 huawei.com~1ascend-1980 16 每个 worker 的卡数、单节点算力和 DP/TP/PP 编排空间。
单 worker memory resources.requests/limits/memory 512Gi 模型加载、训练 batch、Ray object store 和容器 OOM 风险。
共享内存 volumes/1/emptyDir/sizeLimit 128Gi 数据加载、进程间通信、Ray/训练框架临时内存。
服务端上限 MAX_WORKER_REPLICAS 由部署配置控制 限制单次 CI 最大节点数，保护集群资源。

快速冒烟层

目标是尽快验证镜像、网络、submitter API、RayJob 创建、watch 事件和 cleanup 链路。

资源规模可以较小，重点覆盖控制面和基础执行路径。

多机 nightly 层

目标是验证跨节点 Ray 调度、Ascend 多卡资源申请、源码分发、训练脚本启动和关键 E2E 用例。

当前 nightly 采用 2 x 16 拓扑，承担稳定性和回归验证职责。

扩展验证层

目标是验证更大 N x M 拓扑下的通信、batch 配置、内存水位和训练框架并行策略。

扩展前需要同步调整服务端上限、模板资源、watch timeout 和集群容量规划。

2 x 16 是当前 nightly 多机 CI 的落地实例，不是系统模型的边界。 扩展到更多 worker 时，需要同步评估集群容量、`MAX_WORKER_REPLICAS`、模板资源、训练并行策略、batch 配置和 watch timeout。

06 / 生命周期

一次 CI 从触发到清理，分成九个动作

一次 CI 的生命周期包含源码准备、RayJob 提交、模板渲染、RayCluster 创建、wrapper 执行、watch 等待和最终清理。

时序图：submit、watch、cleanup
rendered SVG

主动清理

workflow 的最后一步调用 `DELETE /api/v1/workflows/{GITHUB_RUN_ID}?attempt=N`，删除本次 attempt 创建的 RayJob。

兜底清理

服务默认每 600 秒扫描一次，删除带 `ci.verl/job-id` 标签且创建超过 21600 秒的 RayJob。

最终判定

`/watch` 的 `error` 事件不等于失败，workflow 最终只看 `final` 事件里的 `SUCCEEDED`、`FAILED`、`TIMEOUT` 或 `NOT_FOUND`。

以 nightly_ascend_multinode.yml 为例接入 CI

示例对应 verl 项目主分支中的 nightly_ascend_multinode.yml。 这条流水线每天定时运行一次，当前提交 2 worker x 16 NPU 的多机 RayJob。

workflow 的四个关键动作

  1. 把源码放到共享缓存。Runner checkout 后复制到 `/root/.cache/cicd_test/verl`，让 RayJob Pod 和 worker 能拿到同一份提交。
  2. 生成提交 helper。`submit_and_wait_rayjob.sh` 用 `jq` 拼出 JSON payload，POST 给 submitter，并消费 `/watch` 事件流。
  3. 生成多机 wrapper。`run_multinode_testing.sh` 在 RayJob submitter Pod 中执行，负责复制源码到 `/verl`、安装当前 checkout，并初始化全部 worker。
  4. 提交并等待结果。最后通过 `template_patches` 把 worker 资源调整成 64 CPU、512Gi memory、16 NPU 和 128Gi `/dev/shm`。
端到端通过记录： GitHub Actions run 28231225229 / job 83635714775 展示了一次完整提交、watch、训练执行和 cleanup 的通过样例，作为新 workflow 接入后的对照基线。

从 workflow 到 submitter 的 payload 语义

字段 由谁提供 作用
repository、commit_sha、branch GitHub Actions 环境变量 让服务端知道是哪一个仓库、提交和分支触发了任务，并参与校验和标签生成。
github_run_id、github_run_attempt GitHub Actions 环境变量 生成 RayJob 名称和标签，也是 workflow 结束时批量清理的定位条件。
image workflow env 替换 RayJob submitter、head、worker 容器镜像，必须匹配 submitter 配置里的镜像前缀白名单。
script、args workflow 调用参数 生成 RayJob entrypoint。当前 nightly 示例把 wrapper 作为 script，把真实训练脚本作为 `--script-path` 参数。
template_patches workflow 调用参数 在安全白名单内调整资源、`/dev/shm` 和 Ray 运行参数，不能修改 image、entrypoint、hostPath、安全上下文等字段。

08 / HTTP 接口

workflow 只需要调用 submitter 的 HTTP API

这个项目对外暴露的是一组很窄的 HTTP 接口：健康检查、提交 RayJob、查询状态、观察日志与最终状态、按 workflow attempt 清理。 GitHub Actions 里只需要 `curl` 和 `jq` 就可以完成完整闭环。

接口清单

接口 用途 GitHub Actions 中的使用时机
GET /healthz 确认 submitter 服务可访问，返回 {"status":"ok"}。 提交任务前先探测网络和 DNS。
POST /api/v1/rayjobs 提交一次 RayJob。服务端校验请求、渲染模板、创建 RayJob CR，并返回 job_id。 准备好源码缓存、镜像、脚本和资源 patch 后调用。
GET /api/v1/rayjobs/{job_id} 查询 RayJob 当前归一化状态，以及 KubeRay 原始 jobStatus 和 jobDeploymentStatus。 临时排障或需要单次状态查询时使用。
GET /api/v1/rayjobs/{job_id}/watch?format=ndjson 持续输出 status、log、error、final 事件。 CI 主等待逻辑。只有 final 事件决定成功或失败。
GET /api/v1/rayjobs/{job_id}/logs/stream 只流式读取 RayJob submitter Pod 的原始日志。 一般不作为主流程使用，排查日志链路时可直接打开。
DELETE /api/v1/workflows/{github_run_id}?attempt=N 删除本次 workflow attempt 创建的所有 RayJob。 workflow 最后一步用 if: always() 调用。
提交 RayJob：POST /api/v1/rayjobs workflow run step 中的核心写法 
args_json='["--script-path","/verl/tests/special_npu/your_test.sh"]'
env_json='{}'
patches_json='[
  {
    "op": "replace",
    "path": "/spec/rayClusterSpec/workerGroupSpecs/0/template/spec/containers/0/resources/limits/memory",
    "value": "512Gi"
  }
]'

payload="$(jq -n \
  --arg repository "${GITHUB_REPOSITORY}" \
  --arg commit_sha "${GITHUB_SHA}" \
  --arg branch "${GITHUB_REF_NAME}" \
  --arg github_run_id "${GITHUB_RUN_ID}" \
  --arg github_run_attempt "${GITHUB_RUN_ATTEMPT:-1}" \
  --arg image "${IMAGE}" \
  --arg name_suffix "multinode-e2e" \
  --arg script "/root/.cache/cicd_test/run_multinode_testing.sh" \
  --argjson args "${args_json}" \
  --argjson env "${env_json}" \
  --argjson template_patches "${patches_json}" \
  --arg worker_replicas "${WORKER_REPLICAS:-2}" \
  '{
    repository: $repository,
    commit_sha: $commit_sha,
    branch: $branch,
    github_run_id: $github_run_id,
    github_run_attempt: $github_run_attempt,
    image: $image,
    name_suffix: $name_suffix,
    script: $script,
    args: $args,
    env: $env,
    worker_replicas: ($worker_replicas | tonumber),
    template_patches: $template_patches
  }')"

response="$(curl -sS -X POST \
  "${SUBMITTER_URL}/api/v1/rayjobs" \
  -H "Content-Type: application/json" \
  -d "${payload}")"

job_id="$(printf '%s' "${response}" | jq -r '.job_id')"
等待结果：消费 watch 事件 只以 final 事件判断成败 
final_status_file="/tmp/rayjob-final-status-${job_id}"
rm -f "${final_status_file}"

curl -N -sS \
  "${SUBMITTER_URL}/api/v1/rayjobs/${job_id}/watch?format=ndjson" |
while IFS= read -r event; do
  type="$(printf '%s' "${event}" | jq -r '.type // empty')"

  case "${type}" in
    log)
      printf '%s' "${event}" | jq -r '.line // ""'
      ;;
    status)
      printf '%s' "${event}" |
        jq -r '"[rayjob status] " + (.status // "UNKNOWN")'
      ;;
    final)
      status="$(printf '%s' "${event}" | jq -r '.status')"
      printf '%s' "${status}" > "${final_status_file}"
      ;;
  esac
done

final_status="$(cat "${final_status_file}" 2>/dev/null || true)"
case "${final_status}" in
  SUCCEEDED) exit 0 ;;
  FAILED|TIMEOUT|NOT_FOUND) exit 1 ;;
  *) echo "Watch ended without successful final status."; exit 1 ;;
esac
主动清理：workflow 最后一段固定写法 避免 RayJob/RayCluster 残留占用资源 
- name: Cleanup RayJobs
  if: always()
  run: |
    curl -sS -X DELETE \
      "${SUBMITTER_URL}/api/v1/workflows/${GITHUB_RUN_ID}?attempt=${GITHUB_RUN_ATTEMPT:-1}"
实际 workflow 将提交和 watch 封装成 `submit_and_wait_rayjob.sh`，每个 CI 任务只传 `name_suffix`、`script`、`args_json`、`env_json`、`template_patches_json` 五个参数。 nightly_ascend_multinode.yml 就是这个调用模式。

09 / 变更限制

workflow 修改需要匹配 submitter 校验和部署配置

submitter 在创建 RayJob 前执行请求校验。workflow 修改镜像、脚本、worker 数、env 或 template_patches 后， 常见失败会以 4xx validation error 返回，并在响应体中给出校验原因。

限制项、修改入口和部署动作

限制项 触发失败的典型修改 修改入口 重新部署路径
ALLOWED_REPOSITORY repository 不等于允许仓库。 deploy/deployment.yaml env。 kubectl apply -f deploy/deployment.yaml 后等待 Deployment rollout。
ALLOWED_IMAGE_PREFIXES workflow 换了新镜像仓库或镜像前缀。 deploy/deployment.yaml env。 更新 env 后重新 apply submitter Deployment。
ALLOWED_SCRIPT_PREFIXES script 指向新的共享缓存目录、绝对路径或业务目录。 deploy/deployment.yaml env。 更新 env 后重新 apply submitter Deployment；workflow 中的 wrapper 路径同步调整。
WORKER_REPLICAS / MAX_WORKER_REPLICAS worker_replicas 超过服务端上限，或默认 worker 数大于最大值。 deploy/deployment.yaml env，同时核对 Kueue quota。 更新 submitter Deployment；队列容量变化同时 apply 对应 kueue/*.yaml。
MAX_ARGS / MAX_ARG_LENGTH 训练脚本参数过多、单个参数过长，或参数中包含不安全字符。 deploy/deployment.yaml env；不安全字符校验位于 Go 代码。 数量和长度只改 env；字符规则变化需要改代码、测试、构建镜像、更新 Deployment。
MAX_EXTRA_ENV / MAX_ENV_VALUE_LENGTH workflow 追加 env 太多、value 过长，或使用 PATH、PYTHONPATH、RAY_ADDRESS 等保护 env。 数量和长度在 deploy/deployment.yaml；保护列表在 internal/rayjob/validate.go。 env 上限只改部署配置；保护列表变化需要代码发布。
MAX_TEMPLATE_PATCHES / MAX_TEMPLATE_PATCH_VALUE_LENGTH template patch 数量过多，或 value 超过长度限制。 deploy/deployment.yaml env。 更新 env 后重新 apply submitter Deployment。
template patch 路径白名单 patch image、entrypoint、metadata、hostPath、securityContext、volumeMounts、nodeSelector、affinity、tolerations。 internal/rayjob/template_patch.go。 修改白名单需要补测试，执行 go test ./...，构建并推送 submitter 镜像，再更新 Deployment。
RAYJOB_TEMPLATE_PATH 切换 A2/A3 模板、启用 Kueue 模板，或模板路径不存在。 deploy/deployment.yaml env；模板内容在 templates/verl-rayjob*.yaml。 只改路径时重新 apply Deployment；改模板内容时重新构建镜像并更新 Deployment 镜像。
WATCH_TIMEOUT_SECONDS / LOG_HEAD_WAIT_SECONDS 多机任务排队或训练时间超过 watch 超时，日志 Pod 启动慢导致日志等待提前结束。 deploy/deployment.yaml env。 更新 env 后重新 apply submitter Deployment。
Kueue quota / flavor / queue 资源池不足、硬件标签不匹配、RayJob 未携带 queue 标签或 spec.suspend: true。 kueue/*.yaml、目标 RayJob 模板、命名空间 label。 apply Kueue 资源；模板变化按镜像内置模板发布；命名空间 label 使用 kubectl label namespace 更新。

只改 workflow

镜像前缀、脚本前缀、worker 上限、patch 路径都已经被允许时，只需要修改业务仓库里的 workflow 和训练脚本。

只改部署配置

镜像白名单、脚本白名单、worker 上限、watch timeout、cleanup TTL、patch 数量上限属于 submitter env，更新 deploy/deployment.yaml 后重新 apply。

需要代码发布

新增允许的 patch 路径、改变保护 env、放宽参数字符规则，属于服务端校验逻辑变更，需要测试、构建镜像并滚动 Deployment。

submitter 配置更新后的固定验证 部署生效和 API 可用性 
kubectl apply -f deploy/deployment.yaml
kubectl -n ci-system rollout status deploy/rayjob-submitter

kubectl -n ci-system get deploy rayjob-submitter \
  -o jsonpath='{.spec.template.spec.containers[0].env}'

curl -sS http://rayjob-submitter.ci-system.svc.cluster.local/healthz

10 / 安全调参

template_patches 是受限 JSON Patch，不是任意 YAML 入口

这让 workflow 能应对 OOM、`/dev/shm` 不足、Ray 参数变化等 CI 调参需求，同时不开放任意 hostPath、镜像、权限或调度约束。

允许的第一版范围

目标 路径形态
submitter/head/worker 容器资源 resources.requests/* 和 resources.limits/*
head/worker dshm volumes/1/emptyDir/sizeLimit
head/worker Ray 参数 rayStartParams/*
head/worker env 追加 路径以 /env/- 结尾，只能新增非保护环境变量

禁止 patch 的关键字段

  • metadata、spec.entrypoint、容器 image
  • hostPath、volumeMounts、任意 volumes
  • securityContext、serviceAccountName
  • nodeSelector、affinity、tolerations
  • 受保护 env，例如 PATH、PYTHONPATH、RAY_ADDRESS
JSON Pointer 中资源名里的斜杠要转义，`huawei.com/ascend-1980` 在 path 中写成 `huawei.com~1ascend-1980`。
常见 patch 示例 资源、dshm、Ray 参数、env 
[
  {
    "op": "replace",
    "path": "/spec/rayClusterSpec/workerGroupSpecs/0/template/spec/containers/0/resources/limits/memory",
    "value": "512Gi"
  },
  {
    "op": "replace",
    "path": "/spec/rayClusterSpec/workerGroupSpecs/0/template/spec/volumes/1/emptyDir/sizeLimit",
    "value": "128Gi"
  },
  {
    "op": "add",
    "path": "/spec/rayClusterSpec/workerGroupSpecs/0/rayStartParams/memory-usage-threshold",
    "value": "0.98"
  },
  {
    "op": "add",
    "path": "/spec/rayClusterSpec/workerGroupSpecs/0/template/spec/containers/0/env/-",
    "value": {"name": "RAY_memory_usage_threshold", "value": "0.98"}
  }
]

11 / 接入指南

新的多机 CI 接入流程

新 workflow 通过固定提交协议接入，不直接处理 Kubernetes 细节。 接入时复用 nightly 的结构，并替换镜像、脚本路径和资源 patch。

确认运行环境和网络

runner 需要能解析并访问 `rayjob-submitter.ci-system.svc.cluster.local`，workflow 中可以先调用 `/healthz` 做快速探测。

准备镜像

镜像需要包含训练运行时、Ascend 依赖和基础工具；镜像前缀必须被 submitter 的 `ALLOWED_IMAGE_PREFIXES` 允许。

复制源码到共享缓存

把当前 checkout 复制到 `/root/.cache/cicd_test/verl`，避免 RayJob Pod 使用镜像里的旧源码。

选择入口脚本

`script` 指向共享缓存中的 wrapper，`args` 传真实训练脚本，例如 `/verl/tests/special_npu/...sh`。

声明 worker 规模

按目标拓扑设置 `WORKER_REPLICAS=N`，并通过资源 patch 设置每个 worker 的 `huawei.com/ascend-1980=M`。nightly 当前实例为 `N=2, M=16`。

通过 template_patches 调资源

OOM 时优先 patch worker memory 和 dshm；需要 Ray 行为调优时 patch `rayStartParams` 或追加非保护 env。

消费 watch final 作为结果

helper 应持续读取 `/watch?format=ndjson`，把日志打印到 GitHub Actions，并只以 `final` 事件决定 workflow 成败。

Cleanup 固定收尾

workflow 最后一段使用 `if: always()` 调用 DELETE。后台 stale cleanup 是兜底，不应替代主动清理。

最小 workflow 骨架 nightly 模式的最小化版本 
env:
  SUBMITTER_URL: http://rayjob-submitter.ci-system.svc.cluster.local
  IMAGE: your-allowed-image
  WORKER_REPLICAS: "2"

steps:
  - uses: actions/checkout@v4

  - name: Copy checkout to shared cache
    run: |
      rm -rf /root/.cache/cicd_test/verl
      mkdir -p /root/.cache/cicd_test/verl
      tar --exclude=.git -cf - . | tar -xf - -C /root/.cache/cicd_test/verl

  - name: Prepare helpers
    run: |
      # 写入 submit_and_wait_rayjob.sh 和 run_multinode_testing.sh。
      # 完整实现参考：
      # https://github.com/verl-project/verl/blob/main/.github/workflows/nightly_ascend_multinode.yml

  - name: Run RayJob
    run: |
      /root/.cache/cicd_test/submit_and_wait_rayjob.sh \
        multinode-e2e \
        /root/.cache/cicd_test/run_multinode_testing.sh \
        '["--script-path","/verl/tests/special_npu/your_multinode_test.sh"]' \
        '{}' \
        '[{"op":"replace","path":"/spec/rayClusterSpec/workerGroupSpecs/0/template/spec/containers/0/resources/limits/memory","value":"512Gi"}]'

  - name: Cleanup RayJobs
    if: always()
    run: |
      curl -sS -X DELETE \
        "${SUBMITTER_URL}/api/v1/workflows/${GITHUB_RUN_ID}?attempt=${GITHUB_RUN_ATTEMPT:-1}"

12 / 设计原则

系统边界与职责划分

workflow、submitter 和 RayJob 模板分别承担不同职责，三层边界共同保证 CI 的灵活性、安全性和可维护性。

workflow 负责业务选择

它决定跑哪个提交、哪个镜像、哪个训练脚本，以及这次 CI 需要的资源参数。它不直接创建 Kubernetes 资源。

submitter 负责控制面安全

它校验输入、渲染模板、创建 RayJob、观察状态、读取日志、按 run attempt 清理资源，并处理残留任务兜底。

模板负责集群约束

节点选择、hostPath、NPU 驱动挂载、安全上下文、基础 env 和 RayCluster 结构都在模板中固化。

设计取舍： 系统只暴露 CI 所需的窄接口，而不是把 Kubernetes 和 RayJob 的全部能力交给 workflow。 资源不足时通过白名单 patch 调整 memory 和 `/dev/shm`，Ray 参数需要变化时通过 `rayStartParams` 调整； hostPath、权限、镜像来源和 entrypoint 等高风险字段仍由服务端模板和校验逻辑控制。 这样既保留 CI 调参能力，又避免每条流水线演变成高权限 Kubernetes YAML。

13 / 排障

常见失败信号和定位思路

多机 CI 的失败通常不是单点问题。排查路径按提交前校验、RayJob 创建、集群启动、训练脚本执行和资源清理五类展开。

失败类型对照

现象 优先检查
POST 返回 4xx validation error 仓库名、镜像前缀、script 前缀、branch 格式、template_patches 白名单路径。
wrapper 报 `/root/.cache/cicd_test/verl` 不存在 runner 是否成功复制 checkout，RayJob Pod 是否挂到了同一份 `/root/.cache`。
Ray worker 数量不对 `WORKER_REPLICAS`、模板 worker replicas、`EXPECTED_WORKERS`、KubeRay worker pod 是否调度成功。
OOM 或容器被杀 worker memory、`/dev/shm`、Ray memory threshold、训练 batch 配置。
watch 结束但没有成功 final submitter watch timeout、RayJob CR 状态、RayJob submitter Pod 日志是否完整。

多机规模相关提醒

如果训练使用全部 worker NPU，data parallel size 通常等于 `worker_replicas x 每 worker NPU 数`。 nightly 的 2 x 16 拓扑对应 32。类似 `Got mini_batch_size=16 and self.engine.get_data_parallel_size()=32` 的错误说明 mini batch 不能被 DP size 整除。

当前 nightly 示例通过 worker resource patch 把每个 worker 调到 `64 CPU / 512Gi / 16 NPU`， 同时把 worker dshm 调到 `128Gi`。如果还是 OOM，优先确认训练脚本里 global batch、mini batch、model parallel 和 offload 配置是否匹配目标卡数。

14 / 总结

总结：窄接口承载多机多卡 CI

多机多卡 CI 中最容易失控的部分被收束为一个窄接口：模板固定安全边界，workflow 做可审计的参数化提交，KubeRay 负责实际编排。

总结： 多机 CI 的价值在于把“昂贵资源的临时使用”变成“可提交、可观察、可清理、可复用”的平台能力。 新增流水线复用同一套 submit helper、同一份 RayJob 模板和同一套 watch/cleanup 语义， 训练脚本可以继续快速演进，CI 基础设施保持安全和稳定。
